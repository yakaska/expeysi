# Модель данных и синхронизация

Источник правды для UI — локальная база Room. Firestore хранит общий журнал
изменений семьи: каждое устройство пишет туда свои изменения и слушает чужие.
Если сети нет, Firestore SDK сам держит отправку в офлайн-очереди и доставляет
её при появлении связи.

## Термины

- **Семья** — группа людей с общим журналом учёта: записи всех членов видны
  каждому, к чужим семьям доступа нет.
- **Баланс** — не «сколько денег», а группа счетов с общей валютой, например
  «Основной» в рублях. Несколько балансов позволяют вести учёт в разных валютах.
- **Счёт** — кошелёк внутри баланса: «Наличные», «Карта», свой вариант. Валюту
  счёт наследует от баланса.
- **Операция** — доход или расход, привязанный к счёту, категории и дате.
- **Перевод** — перемещение денег между счетами: хранится парой записей-ног
  («transfer_out» у счёта-источника, «transfer_in» у счёта-получателя),
  связанных общим идентификатором.

## Идентификация и онбординг

- Вход — через Google Sign-In и Firebase Authentication: SDK получает токен
  Google-аккаунта, Firebase обменивает его на учётную запись приложения.
  Идентификатор пользователя (UID) привязан к Google-аккаунту, поэтому
  сохраняется после переустановки и при смене устройства.
- «Семья» — это документ `families/{familyId}`. `familyId` — автогенерированный
  20-символьный ID Firestore, он же код приглашения: передаёшь код второму
  пользователю любым способом (мессенджер, из уст в уста).
- Присоединение: второй пользователь вводит код, приложение создаёт документ
  `families/{familyId}/members/{свой uid}`. Угадать чужой код перебором
  практически невозможно (20 символов, `[a-zA-Z0-9]`). Локальные данные,
  накопленные до присоединения, очищаются.
- Выход: пользователь удаляет свой документ `members/{uid}`, после чего
  приложение очищает локальные семейные данные. Google-аккаунт остаётся
  вошедшим, а семейный журнал сохраняется для остальных участников.

## Структура Firestore

```
families/{familyId}
  name: string                 # имя семьи, задаёт создатель
  createdAt: timestamp
  createdBy: uid

  members/{uid}
    displayName: string
    joinedAt: timestamp
    uid: string

  balances/{balanceId}         # UUID
    name: string               # "Основной", свой вариант
    currencyCode: string       # ISO 4217: "RUB", "USD", ...
    iconKey: string            # ключ иконки из фиксированного набора
    colorKey: string           # ключ цвета обода иконки из общей палитры
    deleted: boolean
    updatedAt: long                # epoch millis для слияния

  accounts/{accountId}         # UUID
    name: string               # "Наличные", "Карта", свой вариант
    iconKey: string
    colorKey: string           # ключ цвета обода иконки из общей палитры
    openingBalanceMinor: long  # начальный остаток в минимальных единицах валюты баланса
    balanceId: string          # баланс, к которому относится счёт; валюта счёта = валюта баланса
    deleted: boolean
    updatedAt: long                # epoch millis для слияния

  categories/{categoryId}      # UUID
    name: string
    iconKey: string            # ключ из фиксированного набора Material Icons
    colorKey: string           # ключ цвета обода иконки из фиксированной палитры
    type: "income" | "expense"
    deleted: boolean
    updatedAt: long                # epoch millis для слияния

  transactions/{transactionId} # UUID
    type: "income" | "expense" | "transfer_out" | "transfer_in"
    amountMinor: long          # сумма в минимальных единицах валюты счёта
    accountId: string
    categoryId: string         # у ног перевода пустой: перевод не имеет категории
    date: long                 # epoch millis (локальная дата автора)
    note: string               # может быть пустой
    linkedId: string           # общий UUID пары ног одного перевода; у остальных пустой
    counterpartyAccountId: string # счёт на другой стороне перевода; подпись «откуда → куда»
    deleted: boolean
    updatedAt: long                # epoch millis для слияния
    updatedBy: uid
```

Справочник валют (ISO 4217, ~230 записей: код, английское название, символ)
живёт только локально в Room (`currencies`), загружается миграцией и посевом при
создании БД. В Firestore не синхронизируется: список одинаковый на всех
устройствах. Упрощение MVP: у всех валют два знака после запятой, даже у
безразрядных вроде JPY.

Балансы группируют счета и задают им валюту: у баланса есть `currencyCode`,
счёт ссылается на баланс через `balanceId`. У счёта поле `currencyCode` —
резервный дефолт, реальная валюта наследуется от баланса. На главном экране
показывается выбранный баланс (выбор хранится локально на устройстве) и суммы
по его счетам за скользящие окна: сегодня, последние 7 дней, последние 30 дней.

## Предзаписанные данные

Категории, счета и баланс по умолчанию имеют детерминированные UUID (константы
в коде), одинаковые на всех устройствах. Сидируются в Room при первом запуске и
в Firestore при создании семьи — повторная запись с тем же ID ничего не
дублирует.

- Баланс: «Основной» (RUB).
- Счета: «Наличные», «Карта» — оба привязаны к «Основному».
- Категории расходов: Еда, Транспорт, Жильё, Одежда, Связь, Здоровье, Подарки,
  Развлечения, Косметика.
- Категории доходов: Зарплата, Премия, Подарки.

Точный список с UUID и ключами иконок —
в `android/app/src/main/java/com/expeysi/app/data/seed/PresetData.kt`.

## Миграции схемы

- Каждая версия схемы Room едет одним изменением: миграция `MIGRATION_(N-1)_N`
  в `AppDatabase.kt`, свежий `N.json` в `android/app/schemas/…` (схемы
  коммитятся) и запись в общий список `ALL_MIGRATIONS` — его регистрирует
  `DataModule` и гоняют тесты.
- Каждый шаг проверяется инструментальным тестом на `MigrationTestHelper`
  против коммитнутых схем (`MigrationStepsTest`, `Migration8To9Test`): база
  старой версии собирается из `N.json`, сырым SQL вставляются строки,
  `runMigrationsAndValidate` накатывает миграцию — и тест сверяет выжившие
  строки, дефолты и данные, которые миграция дозаполняет (сид валют, балансы,
  цвета пресетов). Это правило для каждого нового бампа версии.
- Полный путь 2→9 под списком `ALL_MIGRATIONS` проверяет `MigrationChainTest`:
  открытие через `databaseBuilder` проходит без ошибок, свои строки и запросы
  через DAO целы.
- Шаг 1→2 тестами не покрывается: `1.json` в репозитории нет — схемы коммитят
  с версии 2, а `MigrationTestHelper` не может собрать базу без файла старой
  версии. Миграция состоит из одного `ALTER TABLE`.

## Правила слияния

- Каждое локальное изменение (создание/правка/мягкое удаление) пишется в Firestore
  документом с тем же UUID и свежим `updatedAt`. Метка ставится часами
  устройства, где сделана правка, — при разнице часов «новее» может оказаться
  не та правка, что была сделана позже по-настоящему.
- При получении чужой версии документа: если её `updatedAt` новее локальной —
  перезаписываем локальную; локальную более новую версию отправляем в Firestore.
  Этот подход называется last-write-wins («побеждает последняя правка»).
  Равенство меток игнорируется.
- Удаление мягкое: пишется флаг `deleted = true`, запись продолжает
  синхронизироваться и участвовать в слиянии. Физическая чистка — отдельная
  история, в MVP не делаем.
- После первого снимка realtime-слушателей локальные документы сверяются с ним по
  UUID и `updatedAt`. Полной перезаписи базы при запуске нет: отправляются только
  отсутствующие в Firestore или локально более новые документы. Неизменившееся
  содержимое повторно не пишется: метка времени и автор правки не считаются
  содержимым (иначе переустановка, сиды и расхождение часов гоняли бы пачки
  холостых записей).
- Отключение и повторное подключение realtime-слушателя идёт с растущей паузой
  (5 с, 10 с, 20 с… до 5 мин); `PERMISSION_DENIED` повторов не запускает:
  членство в семье снято сервером, и гонять полные снимки впустую не нужно.
- Сессия семьи поднимается, только когда есть и семья, и вход: восстановление
  Firebase-сессии асинхронно, и запуск синхронизации ждёт его.
- Слушатели снимка стоят, только пока приложение видно пользователю: после ухода
  в фон даётся 10 минут на быстрое возвращение, дальше слушатели снимаются и
  поднимаются на следующем показе экрана. Офлайн-кэш Firestore и Room от этого
  не страдают; телефон в кармане не получает платные realtime-чтения без
  смотрящего экрана.
- Баланс счёта всегда вычисляется: `openingBalanceMinor + доходы − расходы`
  по неудалённым операциям счёта. Ноги переводов двигают остатки так же:
  «transfer_out» уменьшает остаток источника, «transfer_in» увеличивает
  остаток получателя — но в итогах доходов и расходов они не участвуют
  (подробности в разделе «Переводы»).

## Переводы

- Перевод перемещает деньги между счетами — и внутри одного баланса, и между
  балансами разных валют. В экране «+» это третья вкладка рядом с расходом
  и доходом.
- Перевод хранится парой ног, а не одной записью: каждая нога — обычный
  документ `transactions` со своим UUID. Обе ноги несут один `linkedId`; у ноги
  списания (`transfer_out`) сумма — в валюте счёта-источника, у ноги зачисления
  (`transfer_in`) — в валюте получателя; `categoryId` пустой. Посдокументная
  синхронизация last-write-wins при этом не меняется: ноги независимы.
- Суммы конвертации вводятся вручную. Если валюта балансов счетов совпадает,
  сумма зачисления зеркалит сумму списания, пока пользователь не начал её
  править.
- Пара ног, попавшая в один скоуп (один баланс, одна история), показывается
  одной строкой: иконка и подпись «Счёт А → Счёт Б», сумма без знака, нейтральная
  раскраска. Подпись работает и по одинокой ноге — счёт на другой стороне
  хранится в `counterpartyAccountId` на случай, если пара ещё не досинхронилась.
  Одинокая нога без пары в этом скоупе показывается сама по себе и отражает
  движение денег счёта: зачисление — плюс цветом дохода, списание — минус
  обычным цветом.
- Итоги доходов/расходов, разбиения по категориям и счетам, шапки дней ноги
  переводов не учитывают: это перемещения, а не потоки доходов и расходов.
- Редактирование и удаление открываются с любой из ног и действуют на пару.
  Сохранение и удаление пишут только ноги, существующие локально: недостающую
  ногу не восстанавливают новым UUID — после досинхронизации её вторая копия
  пришла бы из Firestore дубликатом.

### Совместимость сборок

Старая сборка приложения (v0.1.x, без поддержки переводов) не знает типов
`transfer_out`/`transfer_in`: по fallback она читает въехавшую по синку ногу
`transfer_in` как обычный расход и занижает остаток получателя. В документах
Firestore маркера версии клиента нет и специально для этого не заводится —
старые сборки не патчат. Поэтому переводами пользуются только после того, как
все члены семьи установили сборку с переводами: второй телефон обновляют до
первого перевода в семье.

## Экспорт и импорт CSV

Импорт и экспорт работают с одним CSV-форматом — тем же, что понимает внешнее
приложение «Бюджет». Из «Бюджета» можно переехать в Expeysi импортом,
а файл экспорта Expeysi возвращается импортом без потерь (round-trip:
файл «туда-обратно» даёт те же данные).

### Формат файла

Заголовок общий с «Бюджетом», разделитель `;`:

```
Дата;Время;Название счета;Категория;Сумма;Валюта;Комментарий
```

- Файл экспорта Expeysi пишется в UTF-8 с BOM. Импорт понимает оба
  разделителя (`;` и `,` — выбирается по заголовку файла) и игнорирует BOM.
- В экране экспорта выбираются типы операций: доходы, расходы и/или переводы.
  Служебные строки и начальные остатки выгружаются всегда.
- После «Комментарий» файл экспорта Expeysi добавляет колонки оформления.
  У файлов «Бюджета» их нет, и импорт читает их, только если они заявлены
  в заголовке.

| Колонка | Что несёт |
|---------|-----------|
| «Иконка категории», «Цвет категории» | иконку и цвет категории |
| «Иконка счета», «Цвет счета» | иконку и цвет счёта |
| «Название баланса», «Иконка баланса», «Цвет баланса» | имя, иконку и цвет баланса, к которому относится счёт |
| «Связка перевода» | общий идентификатор пары ног одного перевода; у остальных строк пустой |

Значения колонок оформления дублируются на каждой строке счёта, включая
служебные: если часть строк потеряется, атрибуты сохранятся на уцелевших.
Пустое значение означает «по умолчанию».

- Начальный остаток счёта идёт служебной строкой с зарезервированной категорией
  «Начальный остаток»: положительный остаток — доход, отрицательный — расход.
  Импорт распознаёт такие строки и ставит счёту `openingBalanceMinor` вместо
  создания операции; категория под это имя не создаётся. Имя зарезервировано
  в редакторе категорий: иначе операции пользователя в такой категории при
  переимпорте превратились бы в остатки.
- Перевод идёт парой строк «расход» и «доход» в категории «Перевод» (списание —
  минус, зачисление — плюс) с общей связкой в «Связке перевода» и иконкой
  перевода в колонках категории: направление кодируется знаком суммы, файл
  читается и внешним «Бюджетом» тоже.
- Экспортируются все активные счета и их активные операции выбранных типов;
  порядок счетов в служебных строках — по имени, операций — по дате.
- Дата и время в колонках — настенные (локальный часовой пояс телефона):
  при экспорте и импорте в одной зоне round-trip точен.
- Валюта счёта — валюта его баланса: в `accounts.currencyCode` живёт резервный
  дефолт, экспорт и импорт на неё не полагаются.

### Как ложится импорт

- Импорт аддитивен и всегда разрешён: балансы и счета создаются новыми,
  существующие не переиспользуются и не изменяются — данные файла ложатся
  отдельной копией рядом с текущими. Неудачный импорт убирается целиком
  удалением нового баланса. Повторная загрузка того же файла тоже разрешена
  и кладёт ещё одну копию; никакой блокировки по «уже импортировано» нет.
  Загрузка обновлённого экспорта создаёт полную копию (старые операции вместе
  с новыми).
- Копия баланса при импорте получает префикс «импорт »: повторный импорт
  «Основного» назовётся «импорт Основной». Если имя занято, добавляется номер
  за максимальным занятым активным: «импорт Основной (2)», «импорт Основной
  (3)»… Баланс без названия в файле получает автосозданное имя
  «Бюджет (валюта)» — так же называет безымянные балансы внешний «Бюджет».
- Счёт группируется по тройке (имя, валюта, баланс): одноимённые счета разных
  балансов не сливаются.
- Новый баланс и счёт берут оформление (иконку, цвет) из первой строки, где
  встретились. Категория — общая на приложение: она переиспользуется по паре
  (нормализованное имя, тип) для привязки операций, иначе список категорий
  засорялся бы дубликатами. Явные иконка и цвет в строке — признак файла
  экспорта Expeysi: они перекрашивают существующую категорию, поднимая
  `updatedAt` для слияния. Файлы «Бюджета» таких колонок не пишут и оформление
  категорий не меняют.
- Строки с общей «Связкой перевода» категорий не создают: пара «расход + доход»
  восстанавливается настоящим переводом — ногами `transfer_out`/`transfer_in`
  со свежей связкой, суммами каждой ноги и заметками из строк; счёт-контрагент
  каждой ноги — второй счёт пары. Round-trip полный: тип, связка, контрагент,
  суммы и оформление переживают файл, аналитика копией совпадает с оригиналом.
- Одиночная нога, чей партнёр отфильтрован из выгрузки, деградирует в обычную
  операцию в категории «Перевод»; связка такой строки теряет смысл.

### Загрузка импорта в Firestore

- Импорт атомарно записывает данные в Room пачками, затем отправляет их в
  Firestore через WriteBatch группами не более 500 документов.
- Ожидание подтверждения батча ограничено таймаутом: если связь подвисла,
  записи остаются в офлайн-очереди Firestore и доставляются сами. Импорт
  не блокируется навсегда.

### Ограничения

- Удалённые записи не экспортируются; счёт с нулевым остатком и без операций
  не экспортируется.
- Файлы переводов старых версий без колонки «Связка перевода» не
  реконструируются: в них перевод восстанавливается парой обычных операций
  в категории «Перевод», остатки совпадают, аналитика копии смешивает перевод
  с доходами и расходами. Такие файлы не ремонтируемы — связки в них не было.
- Импорт меняет только категории существующих данных (перекраска файлами
  экспорта Expeysi, см. выше). Балансы, счета и операции существующие не трогает.
- Операции не дедуплицируются: каждая загрузка кладёт полную копию операций
  файла в её новые балансы; ненужная копия удаляется целиком вместе с балансом.

## Даты и периоды

- День и месяц — по локальному часовому поясу телефона, неделя — с понедельника.
- Главный экран показывает скользящие окна «сегодня / 7 дней / 30 дней»
  (см. раздел о балансе выше). «История» и «Анализ» работают с календарными
  периодами: день, неделя, месяц, квартал, полугодие, год, произвольный
  диапазон дат.
- Суммы считаются по неудалённым операциям.
