# Архитектура синхронизации

Итог отвязки клиентского кода от Firebase. Клиент знает только интерфейсы;
Firebase остаётся единственной реализацией транспорта (своего сервера нет).
Семантика прежняя (LWW по `updatedAt`, отправка без ожидания, первичная
сверка), механика: контракт транспорта `observe` + `push` с `PushResult` и
потоком `rejections`, независимая по документам запись, рабочий цикл движка
на conflated-канале с экспоненциальным backoff, импорт через dirty.
Wire-формат Firestore описан в `docs/data-model.md` и не менялся.

## Слои и зоны

| Зона | Что там | Firebase |
|------|---------|----------|
| `ui/*` | Экраны, ViewModel | нет |
| `data/sync` | `SyncEngine` (движок: слияние, сверка, рабочий цикл) + шов `SyncTrigger` | нет |
| `data/importer` | `BudgetImportService`, шов записи `ImportWriter` | нет |
| `data/csv`, `data/analysis`, `data/seed` | сервисы и репозитории | нет |
| `data/remote` | контракты транспорта: `AuthProvider`, `FamilyRemote`, `SyncRemote`; типы `RemoteUpdate`/`SyncChange`/`SyncKey`/`PushResult`; маппинг wire↔Room: `SyncMapper` | нет |
| `data/remote/firebase` | реализация транспорта: `FirebaseAuthProvider`, `FirebaseFamilyRemote`, `FirebaseSyncRemote`, `ChangePusher` (исполнение записи на узком `PushWriter`), `ChangeBatching` (размер батча, порог и таймаут) | да |
| `di` | связывание: `FirebaseModule` (объекты SDK), `RemoteModule` (биндинги контрактов), `DataModule` (Room, швы `SyncTrigger`/`ImportWriter`, скоуп `@SyncScope`) | да |

Guard: `FirebaseImportsGuardTest` сканирует исходники `src/main` и валит тест
при появлении импорта `com.google.firebase.*` или внутренней зоны
`data.remote.firebase.*` вне `data/remote/firebase/` и `di/`.

## Потоки данных

- Старт. `ExpeysiApp` запускает `SyncEngine.start()`. В инжектированном скоупе
  `@SyncScope` (`SupervisorJob + Dispatchers.IO + CoroutineExceptionHandler`)
  живут три корутины: сессия семьи, подписка на вход и воркер отправки. Сеть
  никогда не вызывается из контекста вызывающего: UI и импортёр только ставят
  запрос прохода в канал воркера.
- Сессия семьи. Запускается по паре «выбранная семья + вход»
  (`FamilyStore.familyId`, `AuthProvider.isSignedIn`): приложение, запущенное
  до входа (familyId сохранён, пользователя ещё нет), поднимает сессию в
  момент входа. `runFamilySync(familyId)` слушает `SyncRemote.observe(familyId)`
  и поток `SyncRemote.rejections`. Входящий `RemoteUpdate` — полное состояние
  типа или дельта (`isFullState`): полное состояние заменяет карту версий типа
  целиком (строка, исчезнувшая из снимка, перестаёт считаться присутствующей),
  дельта — дополняет. Каждое изменение сливается по `updatedAt`
  (LWW, инвариант 1): удалённо свежее или новое — upsert с `dirty = false`;
  локально свежее — `markDirty` и запрос прохода; равные версии — без действий;
  невалидный документ пропускается. Первичная сверка запускается один раз за
  сессию — только когда собраны полные состояния всех четырёх типов
  (`SyncEntityType`: баланс, счёт, категория, транзакция) и в Room появились
  сиды справочников (инвариант 4); при дельтах сверка не запускается никогда.
  Сверка только помечает dirty строки, которых в удалённом состоянии нет или
  чья локальная версия новее, и ставит запрос прохода: прямых отправок из
  слияния и сверки нет.
- Отклонения сервера. Ключ из `rejections` (запись была принята к доставке,
  но позже отклонена сервером) обратно помечается dirty, логируется и получает
  запрос прохода. Повторы подчиняются backoff рабочего цикла; отклонение,
  пришедшее после того как строка успела измениться, безопасно: строка и так
  dirty, лишний `markDirty` — no-op.
- Запись пользователя. ViewModel пишет строку в Room с `dirty = true` в той же
  записи и вызывает `SyncTrigger.trigger()` — немедленно, без ожидания работы.
- Рабочий цикл. Запросы прохода идут через `Channel(CONFLATED)`: N триггеров
  подряд дают не более одного лишнего прохода; триггеры, пришедшие во время
  паузы, не обходят её — после паузы один проход. Один проход (`syncDirty`):
  проверка `familyId` и `userId` (инвариант 7) — без них ничего не
  отправляется и не падает, строки остаются dirty, а проход считается
  завершённым; далее dirty-строки всех четырёх типов одним
  `SyncRemote.push(familyId, changes)`, `PushResult.accepted` перечисляет
  ключи, принятые к доставке. Флаг снимается условно по версии отправленной
  строки, поэтому правка во время отправки не теряется — строка остаётся dirty
  и уходит заново. Проход завершён полностью (все dirty-строки приняты или
  отправлять нечего) — backoff сбрасывается на 5 с; иначе — пауза backoff
  (экспоненциально: 5 с, 10 с, 20 с … потолок 5 минут) и повтор. Частичный
  accepted чистит принятые строки немедленно, непринятые остаются dirty и
  повторяются с backoff — ядовитая запись не блокирует остальные. Ошибки Room
  (чтение dirty, условная чистка) и транспорта пробрасываются воркеру и
  логируются с именем сбойной операции, воркер не убивают: dirty не теряются,
  потому что флаг снимается только после accepted.
- Вход. Подписка на `AuthProvider.isSignedIn` (отдельная корутина скоупа):
  `true` (включая значение на старте) ставит запрос прохода, чтобы строки,
  накопленные до входа, ушли. `userId` транзакций при отправке всегда текущий
  пользователь; fallback строки живёт только в `SyncMapper`.
- Импорт. `BudgetImportService` пишет все строки через шов `ImportWriter`
  (Room-реализация, одна транзакция на весь импорт) с `dirty = true` и один
  раз вызывает `SyncTrigger.trigger()`. Сетевые детали (батчи, подтверждения,
  отказы) импортёру не видны: отправку делает обычный рабочий цикл.
- Онбординг. `FamilyRepository` работает с контрактом `FamilyRemote`:
  `createFamily`/`joinFamily` не ждут подтверждения транспорта — выбор семьи
  происходит локально сразу; `leaveFamily` ждёт 10 с и при сбое всё равно
  очищает локальное состояние. Для транспорта, ждущего ответ сервера, это
  поведение не годится — см. раздел «Что обязана сделать HTTP-реализация
  иначе».
- Выход из семьи. `FamilyDataReset` (контракт, реализация Room) чистит
  семейные строки Room; флаги хранит `FamilyStore`
  (`SharedPreferences`, ключ `family_id`).

## Контракт транспорта

`SyncRemote` — журнал изменений семьи (семья всегда передаётся явно):

- `observe(familyId): Flow<RemoteUpdate>` — один поток обновлений по типам.
  Обновления полным состоянием или дельтой; транспорт сам переживает разрывы
  связи (Firebase: переподключение snapshot-слушателя через 5 с) и не
  пробрасывает исключения наружу.
- `push(familyId, changes): PushResult` — передаёт изменения и возвращает
  принятые к доставке ключи. Реализация сама режет отправку на порции; при
  сбое либо бросает исключение (ничего не принято), либо возвращает
  частичный accepted. Повторная отправка идемпотентна. Семантика accepted
  (KDoc контракта): для Firebase — «передано SDK / офлайн-очереди»
  (инвариант 5), для HTTP — «принято сервером».
- `rejections: Flow<SyncKey>` — ключи, чья запись была принята к доставке
  (попала в accepted), но позже отклонена сервером. Для транспорта, который
  ждёт ответ сервера, поток пустой: отклонённые записи не включаются в
  accepted (KDoc контракта).

Firebase-реализация (`FirebaseSyncRemote`): четыре snapshot-слушателя с
переподключением, каждый снимок — полное состояние типа. Запись независима по
документам: короткая отправка (в пределах одного батча) — отдельный `set()` на
каждый документ без ожидания (инвариант 5), отказ сервера по документу
фиксируется в `rejections`; длинная — батчи по 500, где первые батчи ждут
подтверждения с таймаутом 20 с до первого таймаута, а после него все
отправки идут без ожидания. Отказ батча, не являющийся таймаутом, не валит
отправку: его документы перезаписываются по одному с тем же таймаутом, а
остальные батчи продолжают отправляться. Исключение наружу push бросает
только если не передано ничего. Логика исполнения — `pushChangeBatches` в
`ChangePusher.kt` на узком интерфейсе `PushWriter` (set с колбэком отказа,
set/батч с ожиданием); Firebase-типы остаются только в адаптере; размер
батча, порог режима и таймаут живут в `ChangeBatching.kt` (решение — чистая
функция `pushWaitAcks`). Движку поведение записи не видно: для него это
частичный accepted и поток `rejections`.

## Замена транспорта

Пишутся три класса в новой зоне + биндинги:

1. `XAuthProvider : AuthProvider` — реализация входа.
2. `XFamilyRemote : FamilyRemote` — онбординг семьи (create/join/leave).
3. `XSyncRemote : SyncRemote` — обязательства контракта: observe потоком
   обновлений с самовосстановлением после разрывов; транспорт может отдавать
   полные состояния типа (как Firebase) или дельты (`isFullState = false`);
   push с порциями и честным accepted; rejections — только про отклонения
   после приёма к доставке.
4. Биндинги только в `di` (сейчас `RemoteModule`; при замене — `XModule` там же).

Логика LWW, дефолтов, сверка и сессия семьи живёт в движке (`data/sync`),
маппинг wire↔Room — в `SyncMapper.kt`, на замене транспорта они не меняются.
Движок приспособлен к обоим типам `observe`: полное состояние заменяет карту
версий типа, дельта дополняет; первичная сверка запускается только по
транспортам с полными состояниями, при дельтах — никогда. Известные
ограничения для альтернативных реализаций продублированы в KDoc контрактов
(`SyncRemote`, `FamilyRemote`) и в разделе ниже.

## Что обязана сделать HTTP-реализация иначе

- push ждёт ответ сервера; accepted = подтверждено сервером. Очередь
  недоставленного обеспечивают dirty-флаги и воркер движка — отдельная очередь
  на стороне транспорта не нужна; rejections пуст.
- observe отдаёт дельты (`isFullState = false`) по серверному курсору (seq на
  семью), а не по updatedAt клиента — часы устройств расходятся. Курсор
  хранится на клиенте; при потере курсора — полная перезагрузка журнала
  с `since = 0`.
- первичная сверка при дельтах не запускается никогда (движок так устроен),
  поэтому локальные строки, которых нет на сервере, надо выгружать явно: при
  первом запуске клиента на новом бэкенде все строки помечаются dirty
  (миграция данных).
- `createFamily`/`joinFamily` ждут ответ сервера: иначе код приглашения может
  ещё не существовать, когда второй участник попытается вступить. `joinFamily`
  чистит локальную БД (включая несинхронизированные dirty-строки), поэтому
  вступающий телефон должен вступать только после того, как первый телефон
  отправил всё.
- push частичный: сервер принимает записи пачками по лимиту (500), ответ
  перечисляет принятые ключи; ошибка 4xx по одной записи не должна
  превращаться в исключение всего push — остальные записи уходят,
  отклонённая не попадает в accepted и повторится воркером.
- LWW остаётся по клиентскому `updatedAt`: сервер принимает запись, только
  если `incoming.updatedAt > stored.updatedAt`. Ответ 401 — обновление
  токена и один повтор.

## Тесты

- Движок: `SyncEngineTest` — чистая LWW-матрица (needsUpload) плюс сценарии
  на фейках транспорта и DAO с виртуальным временем: слияние (удалённое или
  локально новее, равные версии, невалидный документ, updatedBy текущего
  пользователя), отправка (гейт по userId и входу, правка во время push,
  частичный accepted, ядовитая запись, объединение триггеров, триггеры во
  время backoff, отсутствие и выбор семьи), отказоустойчивость (повтор после
  сбоя транспорта, ошибка Room в `listDirty`, ошибка Room в `markClean` посреди
  прохода, отмена воркера), backoff (рост 5 с … 5 мин, сброс после полного
  успеха), отклонения сервера (rejections → dirty → повторная отправка),
  сверка (ожидание всех четырёх полных состояний, дельты не сверяются, замена
  карты снимком, отсутствующие в снимках, локально новее), шов trigger.
- Отправка Firebase: `ChangePusherTest` — короткая отправка отдельными set()
  по документам без батча, отказ одного документа (колбэк отказа, остальные
  не затронуты), резка батчами по 500 с ожиданием, отказ батча (перезапись по
  одному без исключения наружу, отклонённые вне accepted), таймаут
  подтверждения (последующие отправки без ожидания, включая перезапись),
  пустая отправка без обращений к транспорту; `ChangeBatchingTest` — порог
  режима отправки и резка на батчи.
- Репозиторий онбординга: `FamilyRepositoryTest`.
- Архитектурный guard: `FirebaseImportsGuardTest` — при появлении запрещённых
  импортов вне `data/remote/firebase/` и `di/` тест падает с указанием пути
  и строки нарушающего файла.
