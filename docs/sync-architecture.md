# Архитектура синхронизации

Итог отвязки клиентского кода от Firebase. Клиент знает только интерфейсы;
Firebase остаётся единственной реализацией транспорта (своего сервера нет).
Семантика прежняя (LWW по `updatedAt`, отправка без ожидания, первичная
сверка), механика пересмотрена по ревью: контракт транспорта `observe` + `push`
с `PushResult`, рабочий цикл движка на conflated-канале, импорт через dirty.
Wire-формат Firestore описан в `docs/data-model.md` и не менялся.

## Слои и зоны

| Зона | Что там | Firebase |
|------|---------|----------|
| `ui/*` | Экраны, ViewModel | нет |
| `data/sync` | `SyncEngine` (движок: слияние, сверка, рабочий цикл) + шов `SyncTrigger` | нет |
| `data/importer` | `BudgetImportService`, шов записи `ImportWriter` | нет |
| `data/csv`, `data/analysis`, `data/seed` | сервисы и репозитории | нет |
| `data/remote` | контракты транспорта: `AuthProvider`, `FamilyRemote`, `SyncRemote`; типы `RemoteUpdate`/`SyncChange`/`SyncKey`/`PushResult`; маппинг wire↔Room: `SyncMapper` | нет |
| `data/remote/firebase` | единственная реализация транспорта: `FirebaseAuthProvider`, `FirebaseFamilyRemote`, `FirebaseSyncRemote`, `ChangeBatching` | да |
| `di` | связывание: `FirebaseModule` (объекты SDK), `RemoteModule` (биндинги контрактов), `DataModule` (Room, швы `SyncTrigger`/`ImportWriter`, скоуп `@SyncScope`) | да |

Guard: `FirebaseImportsGuardTest` сканирует исходники `src/main` и валит тест
при появлении импорта `com.google.firebase.*` или внутренней зоны
`data.remote.firebase.*` вне `data/remote/firebase/` и `di/`. Негативный
прогон зафиксирован: файл-пробник в `data/sync` ловится тестом с точным
указанием пути и строки.

## Потоки данных

- Старт. `ExpeysiApp` запускает `SyncEngine.start()`. В инжектированном скоупе
  `@SyncScope` (`SupervisorJob + Dispatchers.IO + CoroutineExceptionHandler`)
  с самого старта живут две корутины: коллектор сессии семьи и воркер отправки.
  Сеть никогда не вызывается из контекста вызывающего: UI и импортёр только
  ставят запрос прохода в канал воркера.
- Сессия семьи. Движок перезапускается по потоку выбранной семьи
  (`FamilyStore.familyId`, `collectLatest`): `runFamilySync(familyId)` слушает
  `SyncRemote.observe(familyId)`. Входящий `RemoteUpdate` — полное состояние
  типа или дельта (`isFullState`): полное состояние заменяет карту версий типа
  целиком (строка, исчезнувшая из снимка, перестаёт считаться присутствующей),
  дельта — дополняет. Каждое изменение сливается по `updatedAt`
  (LWW, инвариант 1): удалённо свежее или новое — upsert с `dirty = false`;
  локально свежее — `markDirty` и запрос прохода; равные версии — без действий;
  невалидный документ пропускается. Первичная сверка запускается один раз за
  сессию — когда собраны полные состояния всех четырёх типов
  (`SyncEntityType`: баланс, счёт, категория, транзакция) и в Room появились
  сиды справочников (инвариант 4). Сверка только помечает dirty строки,
  которых в удалённом состоянии нет или чья локальная версия новее, и ставит
  запрос прохода: прямых отправок из слияния и сверки нет.
- Запись пользователя. ViewModel пишет строку в Room с `dirty = true` в той же
  записи и вызывает `SyncTrigger.trigger()` — немедленно, без ожидания работы.
- Рабочий цикл. Запросы прохода идут через `Channel(CONFLATED)`: N триггеров
  подряд дают не более одного лишнего прохода. Один проход: dirty-строки
  всех четырёх типов одним `SyncRemote.push(familyId, changes)`;
  `PushResult.accepted` перечисляет ключи, принятые к доставке. Флаг снимается
  условно по версии отправленной строки, поэтому правка во время отправки не
  теряется — строка остаётся dirty и уходит заново. Недобор accepted или ошибка
  push — пауза 5 с и повтор; `CancellationException` пробрасывается, иные
  исключения рабочий цикл не убивают (лог и продолжение). Без выбранной семьи
  проход просто завершается: строки остаются dirty и уходят после выбора семьи
  (сессия стартует с прохода).
- Импорт. `BudgetImportService` пишет все строки через шов `ImportWriter`
  (Room-реализация, одна транзакция на весь импорт) с `dirty = true` и один
  раз вызывает `SyncTrigger.trigger()`. Сетевые детали (батчи, подтверждения)
  импортёру не видны: отправку делает обычный рабочий цикл.
- Онбординг. `FamilyRepository` работает с контрактом `FamilyRemote`:
  `createFamily`/`joinFamily` не ждут подтверждения транспорта — выбор семьи
  происходит локально сразу (риски для HTTP-реализации описаны в KDoc);
  `leaveFamily` ждёт 10 с и при сбое всё равно очищает локальное состояние.
- Выход из семьи. `FamilyDataReset` (контракт, реализация Room) чистит
  семейные строки Room; флаги хранит `FamilyStore`
  (`SharedPreferences`, ключ `family_id`).

## Контракт транспорта

`SyncRemote` — журнал изменений семьи (семья всегда передаётся явно):

- `observe(familyId): Flow<RemoteUpdate>` — один поток обновлений по типам.
  Обновления полным состоянием или дельтой; транспорт сам переживает разрывы
  связи (Firebase: переподключение snapshot-слушателя через 5 с) и не
  пробрасывает исключения наружу.
- `push(familyId, changes): PushResult` — передаёт изменения и возвращает
  принятые к доставке ключи. Реализация сама режет отправку на порции;
  при сбое либо бросает исключение (ничего не принято), либо возвращает
  частичный accepted. Повторная отправка идемпотентна. Семантика accepted
  (KDoc контракта): для Firebase — «передано SDK / офлайн-очереди» (инвариант 5),
  для HTTP — «принято сервером» (реализация сама хранит очередь недоставленного).

Firebase-реализация (`FirebaseSyncRemote`): четыре snapshot-слушателя с
переподключением, каждый снимок — полное состояние типа; push не больше одного
батча идёт одним батчем без ожидания, длинный — батчами по 500, где первые
батчи ждут подтверждения с таймаутом 20 с, а после первого таймаута остальные
уходят без ожидания. Размер батча и
логика ожидания живут только в `ChangeBatching.kt`
(решение — чистая функция `pushWaitAcks`), движку не видны.

## Замена транспорта

Пишутся три класса в новой зоне + биндинги:

1. `XAuthProvider : AuthProvider` — реализация входа.
2. `XFamilyRemote : FamilyRemote` — онбординг семьи (create/join/leave).
3. `XSyncRemote : SyncRemote` — обязательства выше: observe с полными
   состояниями и самовосстановлением, push с порциями и честным accepted.
4. Биндинги только в `di` (сейчас `RemoteModule`; при замене — `XModule` там же).

Логика LWW, дефолтов, сверка и сессии семьи живёт в движке (`data/sync`),
маппинг wire↔Room — в `SyncMapper.kt`, поэтому на замене транспорта не
меняется. Известные ограничения для альтернативных реализаций продублированы
в KDoc контрактов (семантика accepted, отсутствие подтверждения create/join
и т. п.).

## Тесты

- Движок: `SyncEngineTest` — 4 теста чистой LWW-матрицы (needsUpload) плюс
  19 сценариев на фейках транспорта и DAO: слияние (удалённое/локально новее/
  равные версии, невалидный документ), отправка (правка во время push,
  повтор после сбоя и живучесть цикла, частичный accepted, слияние триггеров,
  отсутствие и выбор семьи), сверка (ожидание всех четырёх состояний, дельты
  не сверяются, замена карты снимком, отсутствующие в снимках, локально новее),
  шов trigger.
- Батчи: `ChangeBatchingTest` — решение режима отправки и резка на батчи.
- Репозиторий: `FamilyRepositoryTest` (7 тестов).
- Guard: `FirebaseImportsGuardTest`.
- Итог: 250 unit-тестов, зелёные; из нарушений ktlint остались только
  предсуществующие (7 в main, 4 в test — все в файлах, не тронутых отвязкой).
